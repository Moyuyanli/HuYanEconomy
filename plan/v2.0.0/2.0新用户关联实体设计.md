# 2.0 新用户关联实体设计

## 1. 设计目标

2.0 版本全局数据规范如下：

| 规范 | 统一要求 |
| --- | --- |
| 表名前缀 | 所有业务表必须使用 `hye_` 前缀 |
| 金额类型 | 所有金额字段统一使用 `DECIMAL(19,2)`，Kotlin 使用 `BigDecimal` |
| 时间类型 | 数据库使用 UTC `DATETIME(3)`，Kotlin 使用 `Instant` |
| 经济真源 | 所有实际经济余额和经济变动均以 `Economy-base` 为最底层且唯一真实来源 |

金额字段禁止使用 `Double`、`Float` 或不带小数精度的通用数值类型。时间字段禁止保存格式化字符串；展示时再按用户时区转换。

业务表中的金额字段只用于统计、操作辅助、计算快照和展示优化，不能作为实际扣款、入账、转账或余额判断的最终依据。所有经济操作必须通过 `Economy-base` 的 `EconomyAccount` 完成，并以账户操作结果为准；业务表金额与账户余额不一致时，以 `Economy-base` 为准并执行校正。

用户相关实体统一使用 `hye_user_info.id` 作为内部关联主键：

- `qq` 只表示外部 QQ 身份，并建立唯一约束；
- `user_key` 使用 `u<qq>`，作为业务层稳定标识；
- 所有 `user_id` 字段均引用 `hye_user_info.id`，不得再把 QQ 号写入 `user_id`；
- 实体之间优先使用数据库外键，业务层只负责补充跨列一致性校验。
- 后续新增的用户关联信息一律由业务表通过 `user_id` 反向关联 `hye_user_info.id`，用户主表不增加子模块字段，保持用户核心与业务模块解耦。
- 本设计不考虑 V1/V2 实体迁移兼容；新模型直接作为全新实体实现。

```text
hye_user_info
  |-- 1 : 1 -- hye_user_attribute
  |-- 1 : 1 -- hye_user_equipment
  |-- 1 : 1 -- hye_user_sign
  |-- 1 : N -- hye_user_backpack -- N : 1 -- hye_item
  |-- 1 : N -- hye_title_info
```

## 2. 用户核心实体

表名：`hye_user_info`

```text
id              BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY
qq              BIGINT UNSIGNED NOT NULL UNIQUE
user_key        VARCHAR(16) NOT NULL UNIQUE       # u + qq
name            VARCHAR(64) NOT NULL DEFAULT ''
register_group  VARCHAR(128) NOT NULL DEFAULT ''
created_at      DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
updated_at      DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
```

`user_info` 只保存身份和基本资料，不再保存签到、属性、装备或背包明细。

`equipment_id`、`attribute_id` 不放在主表中。属性和装备表各自通过唯一的 `user_id` 反向关联用户，避免同时维护两套方向相反的外键。

字段含义：

| 字段 | 含义 |
| --- | --- |
| `id` | 数据库内部主键，自增，仅用于实体关联 |
| `qq` | 用户 QQ 号，外部身份标识，唯一 |
| `user_key` | 用户业务唯一 Key，固定为 `u<qq>` |
| `name` | 用户昵称 |
| `register_group` | 用户首次注册时所在群的名称或业务标识 |
| `created_at` | 用户记录创建时间 |
| `updated_at` | 用户记录最后更新时间 |

## 3. 用户属性

表名：`hye_user_attribute`

```text
id          BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY
user_id     BIGINT UNSIGNED NOT NULL UNIQUE
created_at  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
updated_at  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
```

```text
hye_user_attribute.user_id -> hye_user_info.id
```

这是用户的一对一扩展表，属性字段可按玩法逐步增加。删除用户时级联删除属性记录。

字段含义：

| 字段 | 含义 |
| --- | --- |
| `id` | 属性记录主键 |
| `user_id` | 唯一关联的用户主表 ID |
| `created_at` | 属性记录创建时间 |
| `updated_at` | 属性记录最后更新时间 |

## 4. 用户签到

表名：`hye_user_sign`

```text
id                           BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY
user_id                      BIGINT UNSIGNED NOT NULL UNIQUE
sign_time                    DATETIME NULL
continuous_days              INT UNSIGNED NOT NULL DEFAULT 0
last_broken_continuous_days  INT UNSIGNED NOT NULL DEFAULT 0
max_continuous_days          INT UNSIGNED NOT NULL DEFAULT 0
total_sign_days              INT UNSIGNED NOT NULL DEFAULT 0
updated_at                   DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
```

签到状态与用户基本资料分离。`sign_time` 使用数据库 `DATETIME`，应用实体统一使用 `Instant` 或 `LocalDateTime`，禁止在同一模块混用时间戳和日期对象。

字段含义：

| 字段 | 含义 |
| --- | --- |
| `id` | 签到记录主键 |
| `user_id` | 唯一关联的用户主表 ID |
| `sign_time` | 上次成功签到时间，未签到时为空 |
| `continuous_days` | 当前连续签到天数 |
| `last_broken_continuous_days` | 最近一次中断前的连续签到天数 |
| `max_continuous_days` | 历史最大连续签到天数 |
| `total_sign_days` | 累计签到天数 |
| `updated_at` | 签到记录最后更新时间 |

### 5.2 背包实例

表名：`hye_user_backpack`

```text
id                 BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY
user_id            BIGINT UNSIGNED NOT NULL
item_id            BIGINT UNSIGNED NOT NULL
item_code          VARCHAR(64) NOT NULL
item_name          VARCHAR(64) NOT NULL
```

字段含义：

| 字段 | 含义 |
| --- | --- |
| `id` | 背包实例主键 |
| `user_id` | 所属用户主表 ID |
| `item_id` | 关联的物品模板 ID |
| `item_code` | 获得时的物品编码快照 |
| `item_name` | 获得时的物品名称快照 |
| `quantity` | 当前堆叠数量 |
| `is_stackable` | 获得时的可堆叠规则快照 |
| `is_equipped` | 是否已经装备 |
| `unique_attributes` | 物品实例独有的动态 JSON 属性 |
| `created_at` | 物品进入背包的时间 |
| `updated_at` | 背包实例最后更新时间 |

## 8. 外键与删除策略

建议建立以下外键：

```text
hye_user_attribute.user_id  -> hye_user_info.id  ON DELETE CASCADE
hye_user_sign.user_id       -> hye_user_info.id  ON DELETE CASCADE
hye_user_backpack.user_id   -> hye_user_info.id  ON DELETE CASCADE
hye_user_backpack.item_id   -> hye_item.id       ON DELETE RESTRICT
hye_user_equipment.user_id  -> hye_user_info.id  ON DELETE CASCADE
hye_user_equipment.title_id -> hye_title_info.id ON DELETE SET NULL
hye_title_info.user_id      -> hye_user_info.id  ON DELETE CASCADE
```

装备槽位的背包外键可使用 `ON DELETE SET NULL`，避免删除背包实例时阻塞用户数据清理。

## 9. JPA 实体约定

- 实体类建议命名为 `UserInfoEntity`、`UserAttributeEntity`、`UserSignEntity`、`ItemEntity`、`UserBackpackEntity`、`UserEquipmentEntity`。
- 所有表名显式写为 `hye_*`，不依赖 Hibernate 默认命名策略。
- `BIGINT UNSIGNED` 在 Kotlin 中使用 `Long`；项目数据范围必须保证不超过 `Long.MAX_VALUE`。
- 新实体的 `userId` 表示 `hye_user_info.id`，不得复用旧代码中“用 QQ 号充当 userId”的语义。
- 即使实体只保留标量 ID，数据库外键和 Repository 语义也必须保持一致。

### 9.1 包结构

新实体直接放在 `economy-data/.../entity` 下，并按领域分包，例如：

```text
entity/user/UserInfoEntity.kt
entity/user/UserAttributeEntity.kt
entity/user/UserSignEntity.kt
entity/user/UserBackpackEntity.kt
entity/user/UserEquipmentEntity.kt
entity/item/ItemEntity.kt
entity/title/TitleInfoEntity.kt
```

现有 `entity/v1`、`entity/v2` 仅作为旧代码归档，后续统一移动到：

```text
entity/old/v1
entity/old/v2
```

旧实体不参与新模型的关联设计，也不作为新业务写入目标。移动时必须同步调整 import、Hibernate 扫描配置、Converter、Repository 和测试。

### 9.2 时间存储规范

统一采用以下方案：

```text
数据库：DATETIME(3)，保存 UTC，精确到毫秒
Kotlin：Instant
序列化：ISO-8601，例如 2026-08-30T12:34:56.123Z
```

理由：

- `Instant` 表示绝对时间，不受服务器时区影响；
- `DATETIME(3)` 比 `BIGINT` 时间戳更易人工查询和排错，同时避免 MySQL `TIMESTAMP` 的时区自动转换；
- 毫秒精度足以覆盖签到、装备、背包等业务，且不会引入纳秒在数据库中丢失的问题；
- 展示时再按配置时区转换为本地时间，不把 `yyyy-MM-dd HH:mm:ss` 格式化字符串存入数据库。

Hibernate 连接应固定 `UTC` 时区（例如设置 `hibernate.jdbc.time_zone=UTC`）。只有表示“业务日期”而非时间点的字段（如农场结算日）才使用 `LocalDate`；不建议使用 `Int`/`Long` 保存时间戳作为新实体的通用方案。

### 9.3 Instant 便捷使用 API

时间字段统一使用 `java.time.Instant`，并提供公共时间工具，实体和业务代码不得自行重复创建 `Clock` 或手动处理时区：

```kotlin
object EntityTime {
    private val clock: Clock = Clock.systemUTC()

    fun now(): Instant = Instant.now(clock)

    fun Instant.toUtcDateTime(): LocalDateTime =
        LocalDateTime.ofInstant(this, ZoneOffset.UTC)

    fun Instant.toDisplay(zone: ZoneId, formatter: DateTimeFormatter): String =
        atZone(zone).format(formatter)
}
```

审计字段建议提供统一刷新方法：

```kotlin
interface AuditedEntity {
    var createdAt: Instant
    var updatedAt: Instant

    fun touch(now: Instant = EntityTime.now()) {
        updatedAt = now
    }
}
```

新建实体时将 `createdAt`、`updatedAt` 默认设为 `EntityTime.now()`；更新实体时调用 `touch()`。数据库只负责持久化，不负责把字符串格式化为日期。接口输出时再通过 `toDisplay(...)` 按用户或系统时区展示。

## 10. 新模型启用要求

本阶段不处理 V1/V2 数据迁移。旧实体只归档到 `entity/old`，新业务直接使用本设计中的实体和表。

启用新模型前必须完成：

1. 创建全部 `hye_*` 新表及外键；
2. 配置 Hibernate 扫描新的 `entity` 包；
3. 为新实体提供 Repository 和业务服务；
4. 校验所有 `user_id`、装备槽位归属和物品模板引用；
5. 新用户注册时同时初始化属性、签到和装备的一对一记录。

## 11. 钓鱼实体设计

钓鱼系统使用全新实体，不复用旧版钓鱼业务逻辑。所有表名继续使用 `hye_` 前缀：

```text
hye_user_fishing_info  用户钓鱼配置及统计（一用户一条）
hye_user_pond          用户鱼塘（一用户多条）
hye_fishing_log        钓鱼结果流水（一用户多条）
hye_fish               全局鱼类配置
```

关系：

```text
hye_user_info.id -> hye_user_fishing_info.user_id
hye_user_info.id -> hye_user_pond.user_id
hye_user_info.id -> hye_fishing_log.user_id
hye_user_pond.id  -> hye_fishing_log.pond_id
hye_fish.id       -> hye_fishing_log.fish_id
hye_item.id       -> hye_user_fishing_info.default_bait_item_id
hye_item.id       -> hye_fishing_log.bait_item_id
hye_user_backpack.id -> hye_fishing_log.rod_backpack_id
```

### 11.1 `hye_user_fishing_info`

```text
id                    BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY
user_id               BIGINT UNSIGNED NOT NULL UNIQUE
rod_level             INT NOT NULL DEFAULT 1
default_pond_id       BIGINT UNSIGNED NULL
default_bait_item_id  BIGINT UNSIGNED NULL
total_fishing_count   INT UNSIGNED NOT NULL DEFAULT 0
max_fish_size         INT UNSIGNED NOT NULL DEFAULT 0
max_fish_price        DECIMAL(19,2) NOT NULL DEFAULT 0
created_at            DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3)
updated_at            DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3)
```

`default_pond_id` 为默认选中的鱼塘 ID，可以指向其他用户的鱼塘；`default_bait_item_id` 为默认鱼饵物品 ID；统计字段记录累计次数、历史最大尺寸和历史最高结算金额。

字段含义：

| 字段 | 含义 |
| --- | --- |
| `id` | 用户钓鱼配置记录主键 |
| `user_id` | 关联用户主表 ID，每个用户唯一一条 |
| `rod_level` | 当前鱼竿等级 |
| `default_pond_id` | 默认鱼塘 ID，可指向其他用户的鱼塘 |
| `default_bait_item_id` | 默认鱼饵物品 ID，关联 `hye_item.id` |
| `total_fishing_count` | 用户累计完成钓鱼次数 |
| `max_fish_size` | 历史钓到的最大鱼尺寸 |
| `max_fish_price` | 历史单条鱼最高结算金额 |
| `created_at` | 钓鱼配置创建时间 |
| `updated_at` | 钓鱼配置最后更新时间 |

```text
id                    BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY
```

### 11.3 `hye_fishing_log`

```text
created_at     DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3)
```

`level`、`price` 是钓鱼结算时的鱼属性快照；`rod_level`、`bait_item_id`、`fee_amount` 和 `net_income` 用于还原当次结算。日志是结果事实记录，不能依赖后续修改后的鱼或鱼塘配置重新计算历史结果。

字段含义：

| 字段 | 含义 |
| --- | --- |
| `id` | 钓鱼流水日志主键 |
| `user_id` | 执行钓鱼的用户主表 ID |
| `fish_id` | 关联的鱼类配置 ID |
| `pond_id` | 实际发生钓鱼的鱼塘 ID |
| `bait_item_id` | 本次使用的鱼饵物品 ID |
| `rod_backpack_id` | 本次使用的鱼竿背包实例 ID |
| `rod_level` | 本次钓鱼时的鱼竿等级快照 |
| `size` | 本次钓到的具体鱼尺寸 |
| `level` | 本次钓到的鱼等级快照 |
| `price` | 本次鱼类基础结算金额快照 |
| `fee_amount` | 本次鱼塘收取的费用 |
| `net_income` | 本次最终净收益，通常为 `price - fee_amount` |
| `created_at` | 实际完成钓鱼结算的时间 |

### 11.4 `hye_fish`

`hye_fish` 是全局鱼类配置表，不关联用户。沿用现有鱼类配置字段，并将金额和审计时间统一为新模型类型。

字段含义：

| 字段 | 含义 |
| --- | --- |
| `id` | 鱼类配置主键 |
| `level` | 鱼类等级 |
| `name` | 鱼类名称 |
| `description` | 鱼类描述 |
| `price` | 鱼类基础价格 |
| `dimensions_min` | 可生成尺寸下限 |
| `dimensions_max` | 可生成尺寸上限 |
| `dimensions_1` 至 `dimensions_4` | 鱼类尺寸或属性计算参数 |
| `technique` | 鱼类对应的钓鱼技巧参数 |
| `special` | 是否为特殊鱼类 |
| `created_at` | 鱼类配置创建时间 |
| `updated_at` | 鱼类配置最后更新时间 |

### 11.5 删除与一致性

- 删除用户时级联删除其钓鱼配置、鱼塘和钓鱼日志；
- 删除默认鱼塘时将 `default_pond_id` 置空；
- `hye_fishing_log.pond_id` 和 `fish_id` 建议使用 `RESTRICT`，保留历史记录的引用完整性；
- 设置默认鱼塘时允许选择其他用户的鱼塘；写入钓鱼日志前只需校验鱼塘记录存在且当前用户有权钓鱼；
- `rod_backpack_id` 必须指向当前用户背包中的鱼竿实例，不能引用其他用户的背包；
- `total_fishing_count`、`max_fish_size`、`max_fish_price` 和鱼塘次数按普通业务字段维护，不额外引入并发重算机制；
- 所有钓鱼时间字段使用 `Instant`，数据库使用 UTC `DATETIME(3)`。

## 12. 银行与金融实体补充设计

当前银行代码同时存在主银行和私人银行两套逻辑。仅有银行基本信息、资产汇总、存款余额和贷款金额，无法支撑利息结算、部分还款、逾期、破产、债券竞标及资金追踪。因此银行模型必须补充生命周期字段、快照字段和流水表。

所有银行新表使用 `hye_` 前缀；所有用户关联均使用 `user_id -> hye_user_info.id`，不再使用 `owner_qq`、`user_qq`、`borrower_qq` 或 `lender_qq` 作为新实体外键。

### 12.1 经济账户映射

银行和鱼塘的实际资金不保存在业务实体的金额字段中，而是通过 `Economy-base` 的 `EconomyAccount` 管理。账户编码和 Scope 固定如下：

| 业务对象 | account | scope | 用途 |
| --- | --- | --- | --- |
| 银行流动资金池 | `b<bankCode>` | `DEFAULT` | 普通存取款、日常可用资金 |
| 银行放贷资金池 | `b<bankCode>` | `LOAN` | 发放贷款和回收贷款本金 |
| 银行准备资金池 | `b<bankCode>` | `PREPARING` | 风险准备金、偿付准备资金 |
| 用户鱼塘资金池 | `f<pondId>` | `DEFAULT` | 鱼塘收费和鱼塘收益 |

其中 `<bankCode>` 是 `hye_bank_info.code`，`<pondId>` 是 `hye_user_pond.id`。账户创建、余额查询、转账和资金冻结均必须使用上述账户；`hye_bank_asset`、存款、贷款、债券持仓和鱼塘统计中的金额只作为业务投影，不得直接修改后视为资金变动。

银行资金池之间的划转也必须通过 `Economy-base` 完成，例如流动资金池向放贷资金池转入额度时，应同时产生账户流水和业务侧操作记录。

### 12.2 银行主表：`hye_bank_info`

在现有 `bank_info` 基础上保留 `code`、`name`、`description`，并补充：

| 字段 | 含义 |
| --- | --- |
| `id` | 银行主键 |
| `president_user_id` | 行长用户主表 ID |
| `code` | 银行唯一业务编码 |
| `name` | 银行名称 |
| `description` | 银行描述 |
| `status` | `ACTIVE`、`SUSPENDED`、`BANKRUPT`、`CLOSED` |
| `star_level` | 银行星级 |
| `score` | 根据评价计算的评分缓存 |
| `review_count` | 评价数量缓存 |
| `interest_policy` | 利率策略，如固定、随机或按周期调整 |
| `withdraw_enabled` | 是否允许普通取款 |
| `created_at` | 创建时间 |
| `updated_at` | 最后更新时间 |
| `suspended_until` | 暂停服务截止时间，可为空 |
| `bankrupt_at` | 破产时间，可为空 |

旧字段 `owner_qq` 应改为 `president_user_id`；旧的 `interestSwitch` 和 `interest` 不应继续作为散落字段，分别由利率策略和利率配置承载。

### 12.3 资产汇总：`hye_bank_asset`

保留资产池汇总，但增加审计和版本信息：

| 字段 | 含义 |
| --- | --- |
| `id` | 资产记录主键 |
| `bank_id` | 银行 ID，每家银行唯一一条 |
| `total_assets` | 银行总资产 |
| `liquidity_pool` | 可立即兑付的流动资金 |
| `reserve_pool` | 风险准备金 |
| `lending_pool` | 可用于放贷的资金 |
| `version` | 乐观锁版本号 |
| `created_at` | 资产记录创建时间 |
| `updated_at` | 资产汇总更新时间 |

### 12.4 资产流水：`hye_bank_asset_ledger`

这是当前设计缺失但运行必需的审计表：

| 字段 | 含义 |
| --- | --- |
| `id` | 流水主键 |
| `bank_id` | 银行 ID |
| `asset_type` | `LIQUIDITY`、`RESERVE`、`LENDING` 等资金池类型 |
| `amount` | 本次变动金额，收入为正、支出为负 |
| `balance_after` | 变动后的余额 |
| `business_type` | 存款、取款、放贷、还款、债券等业务类型 |

| `operator_user_id` | 发起操作的用户 ID，可为空表示系统任务 |
| `created_at` | 流水发生时间 |

`business_type + business_id` 应具备幂等约束，避免重复记账。

### 12.5 用户存款：`hye_bank_deposit_user`

在余额基础上补充利息结算状态：

| 字段 | 含义 |
| --- | --- |
| `id` | 存款账户主键 |
| `bank_id` | 银行 ID |
| `user_id` | 储户用户主表 ID |
| `deposit_amount` | 当前存款本金 |
| `interest_earned` | 已累计但尚未领取或入账的利息 |
| `interest_rate_snapshot` | 当前计息周期使用的利率快照 |

### 12.6 贷款配置：`hye_bank_loan_config`

| `loan_amount` | 初始贷款本金 |

### 12.8 债券实体

国债和狐券都需要完整生命周期：

| 表 | 必补字段 |
| --- | --- |
| `hye_national_bond` | `status`、`remaining_amount`、`maturity_at`、`redeemed_at`、`updated_at` |
| `hye_bank_national_bond_holding` | `bank_id`、`national_bond_id`、`holding_amount`、`interest_rate_snapshot`、`maturity_at`、`redeemed_at`、`status` |
| `hye_fox_bond` | `status`、`bid_start_at`、`bid_end_at`、`term_days`、`winner_bank_id`、`winner_bid_rate`、`winner_premium`、`maturity_at` |
| `hye_bank_fox_bond_auction` | `fox_bond_id`、`bank_id`、`bid_rate`、`premium`、`status`、`settled_at` |
| `hye_bank_fox_bond_holding` | `bank_id`、`fox_bond_id`、`principal`、`rate_snapshot`、`started_at`、`due_at`、`redeemed_at`、`status` |

竞标记录必须保留出价利率和溢价快照，不能在结算时重新读取当前债券配置。

### 12.9 银行评价：`hye_bank_review`

字段含义：`id` 为评价主键，`user_id` 为评价用户主表 ID，`bank_id` 为被评价银行 ID，`score` 为 1-5 分评分，`comment` 为评价内容，`created_at` 为评价时间，`updated_at` 为修改时间（如果允许修改评价）。

需要明确评价规则：若每个用户每家银行只能评价一次，则增加 `UNIQUE(user_id, bank_id)`；否则必须增加评价修改和撤销状态。

### 12.10 银行删除与一致性

- 银行进入 `BANKRUPT` 或 `CLOSED` 后不物理删除，保留存款、贷款、债券和流水历史；
- `hye_bank_asset`、存款、贷款、债券持仓和评价均通过 `bank_id` 关联银行；
- 用户关联字段全部关联 `hye_user_info.id`；
- 资产流水和贷款还款操作必须支持幂等；
- 所有金额使用 `DECIMAL(19,2)`；
- 所有时间使用 UTC `DATETIME(3)`，Kotlin 使用 `Instant`；
- 银行资金池和鱼塘资金池的实际余额必须读取 `Economy-base` 对应账户；
- 业务表中的金额字段只能作为投影、统计、快照或展示辅助数据，禁止直接执行经济扣减或增加；
- `score`、`review_count`、资产池汇总属于缓存或汇总数据，必须能由明细和流水重新核对。
