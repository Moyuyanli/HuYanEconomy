# 签到功能规则链改造实录

> 定位：**最复杂功能的一次完整迁移样例**。
> 签到的复杂度在本项目里属于第一梯队（多动作、状态副作用、奖励多分支、图片渲染、权限开关全揉在一条流程里），
> 它跑通了，说明规则链与 Feature 垂直包结构能扛住真实业务。后续迁移 bank / backpack / title / redpack / fishing
> 都按本文的过程与坑位清单走。
>
> 配套文档：
> - 结构与判据：`docs/项目开发说明.md` §3.3（必备/可选判定表 §3.3.3）
> - 框架能力与阶段进度：`plan/v2.0.0/40-开发手册/Action规则链系统开发手册.md`
> - 契约细节：`plan/v2.0.0/40-开发手册/Action骨架契约.md`
>
> 代码样板：`economy-core/src/main/kotlin/cn/chahuyun/economy/feature/sign/`

## 1. 为什么拿签到当样板

| 复杂度维度 | 签到的实际情况 | 对改造的考验 |
|---|---|---|
| 动作数量 | 4 个：`core.sign` / `.close` / `.open` / `.refresh` | 一个 feature 里多条动作要分别挂规则，不能只接一条 |
| 状态机 | `sign` / `signTime` / `signNumber` / `oldSignNumber` / `signEarnings` 五个字段联动 | 「纯判断」与「推进状态」必须拆开，否则拦截会留下脏数据 |
| 奖励分支 | 4 档随机金币 + 2 种称号 + 月卡 + 双倍/三倍/补签卡 | 计算逻辑量最大，是最该被 `@Before` 承接的部分 |
| 道具副作用 | 过期卡、损坏卡、已用卡都要登记删除；补签卡还会改连签数 | 规则里允许有副作用，但**顺序**变得有语义 |
| 跨阶段取数 | before / action / after 都要同一份 `UserInfoDto` | 逼出 Provider，且必须区分「共享实例」与「重复查库」 |
| 对外输出 | 图片卡片 + 文本降级 + 引用回复 | 动作本体不能只剩 `return`，要能被拆成可读的结算流水 |
| 权限与开关 | 关闭签到 = 把群加入黑名单权限组 | 权限判定仍留在 `action/`，不能被"规则链化"顺手搬走 |
| 旧资产 | 3 个自定义事件（`BeforeSignEvent` / `SignRewardEvent` / `SignCommittedEvent`） | 事件 → 规则链的映射要一一对上，不能留双轨 |

**结论**：签到覆盖了「多条动作」「前置拦截」「跨阶段共享」「后置副作用」「对外输出」「权限交互」六个面。
这六个面基本是经济类功能的通用骨架，所以它是最合适的第一块硬骨头。

## 2. 改造前的样子

横向包结构下的签到由四处拼成：

```
economy-core/.../usecase/SignUsecase.kt          # 主流程：校验 + 奖励 + 入账 + 扣道具 + 发图 全在一起
economy-core/.../service/UserSignRuleService.kt  # 连签判定/推进
economy-core/.../manager/SignManager.kt          # SignRewardEvent 的监听器集合（名字叫 Manager，却无外部调用方）
economy-core/.../sign/SignEvent.kt               # 三个自定义事件：Before / Reward / Committed
economy-main/.../action/SignAction.kt            # 指令入口
economy-main/.../HuYanEconomy.kt                 # 手工订阅 SignRewardEvent / SignCommittedEvent
```

具体毛病：

1. **扩展点靠隐式约定**：奖励计算与称号检查挂在 `EventPriority.HIGH` 之类的顺序上，框架看不出谁依赖谁。
   `SignRewardEvent` 是"可变事件 + 被多个监听器原地修改"，读代码时无法回答"这次金币到底被谁改过"。
2. **主流程把 5 类职责压在一个方法里**：资格校验、奖励计算、状态推进、持久化、渲染发送。
   任何一处要加玩法（节日翻倍、公会加成）都得改这个方法。
3. **拦截不干净**：重复签到是在主流程里 `if (!sign) return`，此时前面可能已经改过 `oldSignNumber`。
4. **文件角色与命名错位**：`SignManager` 里两个方法只有签到自己调用，却因为"历史上在 manager 包里"被当成对外 API。

## 3. 改造过程（按实际执行顺序）

每一步结束都编译、关键步骤跑测试，**不攒着一次改完再编**。这是本次最有效的纪律。

### 步骤 0：先定结构，再动代码

- 动作：把「Feature 垂直包 + 必备只有 Usecase/Rules + Manager 按需」写进 `docs/项目开发说明.md` §3.3。
- 理由：结构没写清就直接搬文件，会按旧习惯摆位置（本次的 `SignManager` 就是这么留下来的）。
- 产出：§3.3.1 五条硬规则、§3.3.2 目录形态、§3.3.3 必备/可选判定表、§3.3.4 文件角色表。

### 步骤 1：拆动作——四个入口全部 `@Action`

- 动作：`SignUsecase` 的 `sign` / `closeSign` / `openSign` / `refreshSign` 全部标 `@Action`。
- 产出：KSP 生成 `SignUsecaseActions`（4 个方法），`SignAction` 退化为纯映射：
  `指令 → SignUsecaseActions.xxx(event)`。
- 验收：`:economy-main:test` 的 `ActionChainIntegrationTest` 期望集合从 1 个 action 改为 4 个。
- 坑：`@Action` 要求第一个参数是事件；`closeSign`/`openSign`/`refreshSign` 只用到 `event` 本身，
  不会产生警告，但 `sign` 因为主要靠 `ActionContext` 取数，`event` 会成为"未使用参数"——用一行来源日志消费掉（见 §7.B1）。

### 步骤 2：把「能不能签」抽成纯判断，交给 `@Before` 拦截

- 动作：`SignService` 新增 `canSign(dto, reSignTime)`，与 `applySign` 共用私有 `minutesSinceSignable`。
- 规则：`@Before(actionId="core.sign", order=10) rejectIfNotSignable` 返回 `Continue` 或
  `EndWithMessage("你已经签到过了哦!")`。
- 为什么必须先做这一步：拦截语义要成立，前提是**判断本身不改状态**。原来 `sign` 字段既是判定又是结果，
  一个方法里又判断又推进，天然做不了干净拦截。
- 验收：core 测试（`canSign` / `applySign` 口径一致：首次放行、1440 分钟窗口、断签转 `oldSignNumber`）。

### 步骤 3：奖励计算搬到 `@Before(order=20)`，并引入 Provider

- 动作：新增 `SignProvider.signer → SignActor(userInfo/user/subject/message/groupId)`。
- 规则：`@Before(order=20) calculateReward` 里 `SignReward(actor.userInfo)` → 抽权重 → 算金币 → 算倍率 →
  `context.put(SignReward::class, reward)`。
- 关键理由（Provider 的收益不是"少写几行"）：
  - before、action、after 拿到**同一个 `UserInfoDto` 实例**，补签卡在 `@Before` 接回的连签数，结算阶段读得到；
  - 一次指令只查一次库（框架按「类型 + 限定名」缓存）。
- 顺序语义：`order=20 > 10`，保证「被拦截时不执行奖励计算」——因为 `signProp` 里有副作用（补签卡改 `userInfo`）。

### 步骤 4：后置逻辑搬到 `@After`，动作改用**返回值**交结果

- 动作：`SignUsecase.sign` 返回 `SignOutcome?`（qq / gold / signNumber / groupId），不再 `context.put`。
- 规则：`@After(10) logCommitted`、`@After(20) grantSignTitles`（`checkSignTitle` + `checkMonopoly` 从主流程挪出），
  两者都用 `context.actionResult(SignOutcome::class) ?: return` 做判据。
- 为什么用返回值：返回值就是「这次到底成没成」的**唯一判据**，`null` = 没签成（被拦截 / 入账失败）。
  用 `context.put` 会有"put 了但后面失败"的假成功。
- 附带收益：`sign` 从此只剩 9 步不可拆的结算流水，每步一行中文注释，排查时能对着日志定位。

### 步骤 5：删事件三件套，清订阅

- 动作：删除 `sign/SignEvent.kt`；`SignRewardEvent` 降级为普通模型 `SignReward`；
  `HuYanEconomy` 删除对应订阅与 `EventPriority` / `GlobalEventChannel` 导入。
- 映射表（这就是"事件 → 规则链"的通用对照）：

| 旧事件 | 语义 | 新落点 |
|---|---|---|
| `BeforeSignEvent`（可取消） | 前置校验 | `@Before(order)` 返回 `EndSilently` / `EndWithMessage` |
| `SignRewardEvent`（可变载荷） | 流程中段计算与加成 | `@Before` 算好后 `context.put`，或动作内普通领域调用 |
| `SignCommittedEvent` | 完成通知/统计 | `@After(order)` + `context.actionResult(...)` |

- 坑：先删事件还是先补规则要按顺序（见 §7.F2），否则奖励会发两遍。

### 步骤 6：作用域校正——删掉 `SignManager`

- 触发：复核「`randomSignGold` / `signProp` 谁在用」，答案只有签到自己。
- 处置：删除 `SignManager.kt`，两个方法 + `isMonthlyCardActive` 并入 `SignService`；
  `SignReward` 拆成独立 `SignReward.kt`（功能私有模型，平铺在功能目录内）。
- **这一步是整轮改造里最容易被忽略、也最容易复发的**：文件搬过去能编译、能跑，看起来"迁完了"，
  但角色错了，后面每个 feature 都会跟着错。

## 4. 最终形态

### 4.1 文件与必要性

| 文件 | 内容 | 必要性 |
|---|---|---|
| `SignUsecase.kt` | 4 个 `@Action` + `SignOutcome` + 私有渲染/降级/文本抽取 | 必备 |
| `SignRules.kt` | `core.sign` 两条 before + 两条 after；三个管理动作各一条 after 审计 | 必备 |
| `SignService.kt` | ① `canSign` / `applySign`（资格与状态）② `randomSignGold` / `signProp`（奖励计算）③ `minutesSinceSignable` | 按需（复杂，用了） |
| `SignReward.kt` | 一次签到的奖励载体：param / baseReward / multiplier / reply / eventReply / propsToConsume | 按需（私有模型） |
| `SignProvider.kt` | `@Provider("signer")` → `SignActor` | 按需（规则要共享快照，用了） |
| ~~`SignManager.kt`~~ | 无外部调用方，**不建** | — |

### 4.2 动作 × 规则矩阵

```
core.sign
  @Before(10)  rejectIfNotSignable   SignService.canSign → 放行 / EndWithMessage
  @Before(20)  calculateReward       SignService.randomSignGold + signProp → context.put(SignReward)
  ------- SignUsecase.sign：推进状态→取奖励→入账→扣道具落库→拼文案→发图→返回 SignOutcome? -------
  @After(10)   logCommitted          actionResult(SignOutcome) 为 null 则跳过
  @After(20)   grantSignTitles       checkSignTitle + checkMonopoly

core.sign.close / .open / .refresh
  @After(10)   logClosed / logOpened / logRefreshed   审计日志（事件强转失败静默跳过）
```

### 4.3 单次签到的数据流

```
GroupMessageEvent
  └─ SignAction → SignUsecaseActions.sign(event)        指令只做映射
       └─ ActionEngine.invoke("core.sign", event)
            ├─ @Before(10) ── provide(SignActor) ──┐   Provider 首次加载：查一次库
            ├─ @Before(20) ── provide(SignActor) ──┤   命中缓存，同一 UserInfoDto 实例
            ├─ SignUsecase.sign ───────────────────┤   context.get(SignReward) / provide(SignActor)
            ├─ @After(10)  ── actionResult ────────┤
            └─ @After(20)  ── provide(SignActor) ──┘
```

### 4.4 职责边界（迁移其它功能时照抄这张表）

| 该做的事 | 落点 | 不该做的事 |
|---|---|---|
| 指令匹配、权限注解 `@MessageAuthorize` | `economy-main/action/` | 在 action 里写业务判定 |
| 主流程编排、对外输出（消息/图片）、返回值快照 | `<Feature>Usecase` | 把奖励计算、称号检查塞回主流程 |
| 可拦截的前置校验、可插拔的计算/加成、完成后的副作用 | `<Feature>Rules` | 用事件 + 优先级表达顺序 |
| 纯判断、纯计算、状态推进（对内） | `<Feature>Service` | 把只有自己用的计算放进 Manager |
| 跨阶段共享的取数 | `<Feature>Provider` | 每个阶段各查一次库 |
| 功能之外要读本功能的信息 | `<Feature>Manager` | 为"结构完整"建空 Manager |

## 5. 关键取舍（结论 / 理由 / 为什么不选另一条）

| 决策 | 结论 | 理由 | 替代方案为何不选 |
|---|---|---|---|
| 动作粒度 | 4 个独立 actionId | 规则链按 actionId 挂规则；合并成 1 个动作就要在内部再分支，等于把规则链降级成 if-else | 单动作 + 指令参数分支：规则无法针对性挂载，审计规则也会误伤 |
| 资格判定 | `canSign`（纯）+ `applySign`（推进）两个入口 | `@Before` 拦截必须无副作用 | 只留 `applySign`：拦截时已改状态，重复指令会搅乱连签 |
| 跨阶段数据 | Provider 产出 `SignActor` | 单实例 + 单次查库 | 各阶段自己 `getUserInfo`：补签卡改的结果传不下去 |
| 结果传递 | 动作**返回值** + `actionResult` | 单一成功判据，`null` 即未成功 | `context.put`：会出现"put 了但入账失败"的假成功 |
| 奖励计算位置 | `@Before(20)` 规则内 | 加成类玩法可插拔，动作不动 | 放动作里：每加一种加成都要改结算流水 |
| 补签卡位置 | 暂留 `signProp`（已知副作用） | 改动最小、行为不变 | 下沉到动作：前置规则变纯计算，但要重排文案与扣卡时机，留待单独立项 |
| Manager | 不建 | 无外部调用方 | 保留 `SignManager`：虚构对外契约，误导读代码的人 |

## 6. 本次踩到的坑（按发现顺序）

1. **`SignManager` 惯性命名**：搬文件时"原来叫这个"，没查调用方。→ 删掉，并入 Service。
2. **`@Action` 事件参数未使用产生警告**：`sign` 主要靠 `ActionContext`。→ 用一行来源日志消费。
3. **`context.put` 与返回值并存导致判据分裂**：一度两套都在用。→ 统一为返回值 + `actionResult`。
4. **`signProp` 的补签卡在 `@Before` 改状态**：order 必须严格大于资格校验。→ 已固定 `10 / 20`，并写进规则注释。
5. **`SignProvider` 注解参数写法与注释不一致**：注释说"写的是字面量"，代码写的是 `const val SIGNER`。
   KSP 确实把 const 解析成了 `"signer"`（生成物可验证），但注释误导。→ 注释改为"必须编译期常量"的准确表述（见 §7.C1）。
6. **旧包编译产物残留**：删除 `economy/sign/` 后 `build/classes` 里可能有空目录或旧 class，打包时会混进 jar。→ 删完查 `build/classes` 与 jar 条目。
7. **`economy-main/src/test/java/Test.java` 构造参数不匹配**：图片预览工具与 `FishingInfoCard` 字段数早已不一致，
   导致 `compileTestJava` 失败，看起来像"这次改动弄坏了"。→ 按现有 8 字段对齐。

## 7. 容易犯的问题清单

格式：**症状 → 根因 → 正确处理**。每条都对应本次真实遇到或差点遇到的问题。

### A. 作用域与文件形态

**A1. 把旧 `manager/` 的类原样搬成 `<Feature>Manager.kt`**
- 症状：文件搬过去能编译、能跑，看起来迁移完成；但里面全是只有本功能调用的方法。
- 根因：按"它以前叫 Manager"决定落点，而不是按调用方。
- 正确处理：先 `grep -rn "XxxManager\."` 看调用方。**调用方全在本 feature 内 → Service（甚至并进 Usecase）**；
  有功能之外的调用方 → 才建 Manager，并把对外契约写清楚。
- 本次实例：`randomSignGold` / `signProp` → `SignService`。

**A2. 为结构对称铺满 5 个文件**
- 症状：出现 `object XxxProvider {}`、`object XxxManager {}` 这种空壳。
- 根因：把"目录里有 5 个文件"当成完成标准。
- 正确处理：必备只有 `Usecase` + `Rules`（`Rules` 允许空壳，它宣告扩展点在这）；
  Service 有重复/复杂逻辑才抽；Provider 真写了 `@Provider` 才建；Manager 有外部调用方才建。
- 本次实例：先建过空的 `SignProvider.kt`，删掉；真需要 Provider 时再建（这次确实需要）。

**A3. 把权限判定也搬进规则链**
- 症状：规则里开始出现 `checkUserHasPerm`，管理员判定分散在两处。
- 根因：把"规则链化"理解成"所有 if 都变成规则"。
- 正确处理：**指令层管"谁有资格触发"（`@MessageAuthorize`），规则链管"业务上此刻能不能做"**。
  权限注解留在 `action/`，`SignUsecase` 里已有的权限代码不再重复判断。
- 本次实例：`closeSign` / `openSign` 保留 `@MessageAuthorize(userPermissions = [OWNER, ADMIN])`，规则只做审计日志。

**A4. 跨 feature 直连对方 Service**
- 症状：B 功能 `import ...feature.a.AService` 直接调。
- 根因：Service 是 `object`，编译器不会拦。
- 正确处理：跨 feature 只走对方 `Manager`；发现对方没有 Manager 却需要被调，说明**该补 Manager**，
  而不是"顺手调 Service"。文档 §3.3.4 / §3.3.6 已收紧此条。

### B. 规则链契约

**B1. `@Action` 的事件参数用不上**
- 症状：`w: Parameter 'event' is never used`。
- 根因：`@Action` 契约要求第一个参数是事件，但业务数据都在 `ActionContext` 里。
- 正确处理：用一行来源日志消费（`Log.info("签到指令:群(..) 用户(..)")`），既有排查价值又消警告。
  生成侧无参数规则也会遇到同类问题，KSP 已生成 `{ _: ActionContext -> }` 规避。

**B2. `@Before` 里带状态副作用且顺序不当**
- 症状：重复签到被拦截，但用户的连签字段已经被改了一次。
- 根因：把"有副作用的规则"排在"校验规则"前面，或干脆只用一个 `@Before` 又判又改。
- 正确处理：`@Before` 尽量纯；**有副作用的一定排在纯校验之后**；order 间距留 10，方便后续插规则。
- 本次实例：资格校验 10 / 奖励计算 20；`signProp` 的补签卡副作用因此被自然保护。

**B3. `@After` 拿不到动作结果**
- 症状：后置日志永远不打印，或 `ClassCastException`。
- 根因：动作用**返回值**交结果，规则却 `context.get(SignOutcome::class)`（`put` 过的才有）。
- 正确处理：读返回值用 `context.actionResult(Type::class)`；它只在动作真的执行过时才有值，
  被拦截或抛异常时为 `null`，直接 `?: return`。
- 附注：`ActionContext` 内部用 `hasActionResult` 区分"动作执行了但返回 null"与"动作根本没执行"，
  真需要区分时查执行详情，不要靠 `get` 猜。

**B4. 拦截文案与旧实现不一致**
- 症状：迁移后玩家反馈提示变了。
- 根因：重写时顺手优化了文案。
- 正确处理：迁移阶段**行为与文案零变化**，要改文案另开一次改动。
- 本次实例：`EndWithMessage("你已经签到过了哦!")` 与原实现逐字一致。

**B5. 每个阶段各查一次库**
- 症状：一次签到查 3 次 `getUserInfo`，且补签卡接回的连签数在结算时"消失"。
- 根因：没引入 Provider，或 Provider 的返回类型不一致（各写各的 DTO）。
- 正确处理：把「跨阶段复用的一份快照」定义成一个类型，用 `@Provider` 提供；
  框架按「类型 + 限定名」在一次调用内缓存，不重复执行。

**B6. Provider 里用 null 表示"取不到"**
- 症状：`provide` 返回 null，或编译期校验报"Provider 返回类型不能为空/Unit"。
- 根因：Provider 契约要求返回非空非 Unit；"取不到"是业务语义，不是接线语义。
- 正确处理：接线问题（事件类型不符、缺上下文）**直接抛异常**，装配期暴露；
  业务上"没这个人/没这条数据"由一个明确的结果类型表达，别用 null 混过去。

**B7. 管理类动作的 `@After` 强转事件炸掉**
- 症状：非群消息触发时后置规则抛 `ClassCastException`。
- 根因：直接 `context.event as GroupMessageEvent`。
- 正确处理：`as? GroupMessageEvent ?: return`；审计规则对不符合的事件静默跳过。
- 本次实例：`logClosed` / `logOpened` / `logRefreshed` 三处。

### C. KSP 与生成物

**C1. 注解参数不是编译期常量**
- 症状：Provider 生成了但 `@FromProvider("signer")` 找不到它；生成物里 `qualifier = ""`。
- 根因：KSP 读注解参数是 `arguments.firstOrNull { it.name == "qualifier" }?.value as? String`。
  只有**编译期常量**会被解析成字符串；`val`（非 `const`）、函数调用、字符串拼接、`when` 表达式都拿不到。
- 后果按参数不同（别一概而论）：
  - `@Action` / `@Before` / `@After` 的 `actionId` → 空串 → **编译报错**（"actionId 不能为空"）；
  - `@Provider(qualifier = ...)` / `@FromProvider(...)` → `orEmpty()` → 空串，**无任何编译错误**；
  - `@Provider(actionId = 非常量)` → `takeIf { isNotBlank() }` → `null` → **静默变成全局 Provider**（最危险）。
- 正确处理：注解参数写 `const val` 或字面量；改完去看生成物里到底写出了什么，不要只信编译通过。
- 本次实例：`@Provider(qualifier = SIGNER, ...)` 中 `const val SIGNER = "signer"` 已被正确解析
  （`EconomyCoreActionModule` 里是 `qualifier = "signer"`）。跨模块 const 未实测，保守起见直接在注解里写字面量。

**C2. `@Provider` 的 qualifier 与 `@FromProvider` 的字符串不一致**
- 症状：运行期抛"找不到匹配 Provider"或"存在多个候选"。
- 根因：两处字符串各写一遍，改一处忘另一处。
- 正确处理：定义 `const val SIGNER`，代码侧引用常量；注解侧（受 C1 限制）用常量/字面量并**两处同时改**。
  规矩：新增 Provider 时先写常量，再写注解，再写 `@FromProvider`。

**C3. 手改生成物或找错生成物位置**
- 症状：改了 `build/generated/ksp/` 下的文件，下次构建被覆盖；或找不到 facade。
- 根因：不清楚两类生成物的落点规则。
- 正确处理：`<Owner>Actions` facade **跟随声明方包**（`feature/sign/`），
  模块描述固定落 `cn.chahuyun.economy.actionchain.generated.<ModuleId>ActionModule`。
  一律不手改，改源码。

**C4. 新增业务模块忘了登记**
- 症状：写在 feature 里的动作完全不生效，日志里也没有，KSP 也不报错。
- 根因：`economy-main` 的 `ActionChainBootstrap.modules` 是**显式清单**，没登记就不会被 install。
- 正确处理：新增模块三件套一起改：`build.gradle.kts` 加 `id("com.google.devtools.ksp")` +
  `ksp(project(":economy-action-ksp"))` + `ksp { arg("actionchain.moduleId", "...") }`；
  然后到 `ActionChainBootstrap` 登记；最后看启动日志里的模块/动作明细确认。
- 本次实例：签到改动后多次确认 `registeredActionIds` 含 4 个 action（集成测试也锁了这条）。

**C5. moduleId 与生成类名对不上**
- 症状：找不到 `EconomyCoreActionModule`。
- 根因：`moduleId = "economy-core"` 会被转成 `EconomyCoreActionModule`（连字符分段首字母大写）。
- 正确处理：按 `economy-core → EconomyCoreActionModule`、`economy-game → EconomyGameActionModule` 的规律找；
  不要手写 import 猜名字。

### D. 构建与测试

**D1. Gradle 带沙箱跑**
- 症状：构建卡住不动，守护进程 CPU 0%，日志停写。
- 根因：沙箱把外网黑洞化，Gradle 卡在 TCP `SYN_SENT`，且**没有超时**。
- 正确处理：依赖已缓存时加 `--offline`；不要在沙箱里跑联网构建。

**D2. `journal-1.lock` 拒绝访问**
- 症状：`Could not open ... caches\journal-1\journal-1.lock`。
- 根因：IDE 的 Gradle 同步正在写同一个缓存。
- 正确处理：等 IDE 同步结束再重试；不是 ACL 问题，不要去改权限。

**D3. compile-testing 测 KSP**
- 症状：内联 `actionProvider<T>` 报 `JVM target 8` 不兼容；或找不到 KSP 支持。
- 根因：`kotlin-compile-testing` 主包不含 KSP 扩展；默认 JVM target 太低。
- 正确处理：依赖加 `kotlin-compile-testing-ksp:1.5.0`，并显式 `jvmTarget = "11"`；
  `JvmTarget` 类不在 compile-testing 主包，别 import 它。

**D4. 旧包产物残留**
- 症状：源码已删，jar 里仍有旧类；或 `build/classes` 里留着空目录导致后续判断失误。
- 根因：Gradle 增量编译不会清理"源码已删除"的产物目录中所有情况。
- 正确处理：删包后查 `build/classes/.../<旧包>` 与 jar 条目（`jar tf`）；
  发现残留就手动清目录再打包。本次对 `SignManager` 专门做了这条检查。

**D5. 测试代码拖累主流程**
- 症状：`compileTestJava` 失败，看起来像业务改动坏了。
- 根因：历史遗留的测试/工具类（`Test.java` 图片预览）构造参数早已与实际模型不一致。
- 正确处理：先判断失败点是不是本次改动引入；不是就顺手对齐，别让它一直挡路。

### E. Mirai 与业务兼容

**E1. 图片渲染/发送失败没有兜底**
- 症状：签到成功但玩家什么都收不到。
- 根因：`buildUserInfoCard` / `sendImage` 抛异常被吞或直接返回。
- 正确处理：渲染与发送都 `runCatching`，失败走文本降级；降级要保留同一份面板文本，
  不能只发"签到成功"。
- 本次实例：`sendSignImage` → `sendSignFallback`，两条失败路径都覆盖。

**E2. 图片面板被塞进引用回复原文**
- 症状：图片信息区第一行是被回复的指令内容。
- 根因：把整条 `MessageChain` 直接按行拆，`QuoteReply` 等非文本元素也被算进去。
- 正确处理：只取 `PlainText`、按 `\n` 拆、`trim`、去空行；这样两个用途（消息链 vs 图片文本）才能共存。

**E3. 跨日边界的时间窗口**
- 症状：极少数情况下"被判定可签，但推进时返回 false"。
- 根因：判定与推进是两次调用，重置点可能正好落在中间。
- 正确处理：动作里对 `applySign` 的返回值**再判一次**（防御），失败就回提示并返回 `null`，
  让后置规则自然跳过。不要让第二次判定抛异常。

**E4. 异步切线程漏掉**
- 症状：画图卡住事件处理线程，群里消息延迟。
- 根因：图片渲染是重 CPU 操作，必须在线程池执行。
- 正确处理：渲染包在 `withContext(EconomyAsyncService.coroutineDispatcher())` 里；落库仍在原上下文。

### F. 迁移纪律

**F1. 一次只搬一个 feature，搬完立刻编译 + 测试**
- 症状：一次改 3 个功能，报 40 个错，不知道哪个是根因。
- 正确处理：`Usecase` 建好 → 编译；规则加好 → 编译；删旧文件 → 全模块测试。每步都能回滚。

**F2. 新旧双轨并行导致逻辑跑两遍**
- 症状：签到一次，金币发两次；或称号检查执行两次。
- 根因：新规则已经挂上，旧事件订阅没删；或旧方法还在主流程里被调。
- 正确处理：**删订阅与挂规则放在同一次改动里**；删完 `grep` 旧事件名确认零引用。
  本次顺序是：先把 `SignRewardEvent` 降级成普通模型 `SignReward`（让它不再能被 broadcast），
  再把逻辑搬进规则，最后删订阅与事件文件。

**F3. 删除顺序不稳定**
- 症状：`git rm` 报路径不存在；jar 里新旧包混在一起。
- 正确处理：建新 → 改引用（含测试、文档示例）→ 删旧 → `grep` 残留 → 查 `build/classes` 与 jar → 跑测试。

## 9. 其它功能的迁移预判

按"改造难度 / 主要风险 / 建议起手"排序，供排期参考。

| 功能 | 难度 | 主要风险 | 建议起手 |
|---|---|---|---|
| **bank（银行）** | 中 | 存款/取款/利息/利率配置多条动作；利息计算带时间差 | 先按动作拆 3~4 个 `@Action`；把"能不能存取"抽成纯判断；利息计算进 Service；管理员改利率的审计走 `@After` |
| **backpack（背包）** | 中高 | 查询类动作多（分页/筛选），输出以图片为主；道具使用会改多张表 | 查询动作不需要 before 规则；"使用道具"要有资格校验 + 后置消耗；先把图片降级路径补齐再迁 |
| **title（称号）** | 中 | 称号授予分散在多个功能里（`TitleManager` 被签到/钓鱼/大富翁共用） | `TitleManager` 属**跨功能共享**，暂留 `manager/`；先迁"称号查询/切换"，不迁被别处调用的授予方法 |
| **redpack（红包）** | 高 | 并发抢红包、金额拆分、超时退款，状态机复杂 | 先用规则链表达"能否抢/是否重复抢"，金额拆分留在 Service；**不要**把并发控制搬进规则 |
| **transfer（转账）** | 中 | 双方账户 + 手续费 + 限额，事务边界清晰但校验多 | 典型 `@Before` 校验（余额/限额/自转）+ 动作内一次性转账；适合作为"校验多"的第二个样板 |
| **fishing（钓鱼）** | 高 | 已在新实体上重建，但仍是 `game/fishing` 横向包；会话/冷却/尺寸/排行 | 先把包改成 `feature/fishing`，再把「抛竿 → 拉起」做成两个动作（`game.fish.cast` / `game.fish.pull`），冷却与资格进 `@Before` |
| **lottery / farm** | 中 | 玩法循环多、随机分支多 | 先接"主循环动作"，复杂随机规则留在 Service，别急着规则化 |

**共同经验**：

1. **先纯校验、再计算、最后副作用**——这个顺序能让绝大多数功能一次通过。
2. **查询类动作往往不需要规则链**：没有扩展点就不必硬挂规则（`Rules.kt` 允许空壳）。
3. **被多个功能共用的 Manager（`TitleManager` / `BackpackManager` / `UserCoreManager`）不要急着拆**，
   等它有了明确的"所属功能"再迁，否则会把共享依赖变成 feature 之间互相 import。
