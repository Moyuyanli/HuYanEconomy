# 经济后端可切换方案（economy-base / mirai-economy）

更新时间：2026-10-20
状态：设计稿（未落地代码）

## 1. 需求

- `mirai-economy` 从"硬前置"降级为**可选依赖**：默认不装也能正常启动、正常交易。
- 配置文件里手动开启，且只有**上游插件已安装**时才真正切到 `mirai-economy`。
- 其余情况始终使用 `economy-base`（本仓库自建账户）作为经济底层。
- 未开启 / 探测失败时，插件不能因为类缺失而启动失败。

## 2. 现状盘点（决定了方案形状）

### 2.1 调用面

`EconomyUtil`（`economy-core/utils`，883 行）是唯一的资金入口，被 21 个文件调用。它的方法分两类：

| 类型 | 方法 | 能否两套后端通吃 |
| --- | --- | --- |
| A. 只吃 `User` / `(id, desc)` / 金额 | `getMoneyByUser`、`getMoneyByBank`、`turnUserToUser`、`turnUserToBank`、`plusMoneyToUser`、`minusMoneyToUser`、`*ForId`、`getBankTotalCached`、`Cheat` | 可以，签名零改动 |
| B. 上游类型进出 | `plusMoneyToWalletForAccount(EconomyAccount)`、`plusMoneyToBankForAccount`、`getMoneyByBankForAccount`、`turnBankAccountToUserWallet`、`getAccountByBank(): Map<EconomyAccount, Double>` | **不行**，必须换参数/返回类型 |

B 类影响 6 个文件：`FundingUsecase`、`BankUsecase`、`BankTaskManager`、`RedPackManager`、`PrivateBankService`、`PrivateBankBankruptcyService`；`UserCoreManager.getUserInfo(account: EconomyAccount)` 是配套的反查重载。

### 2.2 关键事实

- 上游账户 uuid 与本项目 `UserInfoDto.id` 同源（`PrivateBankService` 直接 `EconomyService.account(userInfo.id, null)`，`UserCoreManager` 用 `account.uuid` 反查 `UserInfoDto`），所以**迁移映射有据可依**：上游 `uuid` ↔ `UserInfoDto.id` ↔ `qq`。
- `economy-base` 的 `EconomyCore.init()` 已随启动执行，`economy_account` / `economy_scope` 表始终存在，可作迁移落点。
- `EconomyUtil.init` 现在只 `catch (UnsupportedOperationException)`。上游类缺失抛的是 `NoClassDefFoundError`（`Error`，不是 `Exception`），**会直接炸启动**——这是"可选依赖"必须解决的第一个问题。
- `BaseModuleBoundaryTest` 禁止 `economy-base` 引用 `xyz.cssxsh.mirai.economy`，所以上游实现只能放 `economy-core`。

## 3. 总体思路

三层 + 一个选择器，业务代码不感知后端：

```
业务（usecase / manager / privatebank / feature）
        │  EconomyUtil（兼容门面，签名不变，委托 ↓）
        ▼
EconomyLedgerProvider.current : EconomyLedger      ← 启动时按配置 + 探测决定
        ├── BaseLedger            （economy-base，默认）
        └── MiraiEconomyLedger    （economy-core，上游类只出现在方法体内）
```

- **账本位置**（`LedgerOwner`）是唯一跨后端概念，两套实现各自映射到自己的账户模型。
- 金额统一 `BigDecimal`；`EconomyUtil` 的 `Double` 签名保留到 P3 再淘汰。
- 后端**运行期不可热切**：切换必须"停服 → 迁移 → 改配置 → 启动"，避免交易中换账本。

## 4. 抽象接口

放 `economy-base`，新包 `cn.chahuyun.economy.base.ledger`（不引上游、不引业务包，边界测试仍通过）：

```kotlin
sealed interface LedgerOwner {
    data class Wallet(val qq: Long) : LedgerOwner                 // 用户钱包
    data class UserBank(val qq: Long) : LedgerOwner               // 用户主银行
    data class PluginAccount(val id: String, val description: String) : LedgerOwner  // 插件私有资金（私银准备金、库存池…）
    data class GlobalAccount(val id: String, val description: String) : LedgerOwner  // 全局银行子账户
}

enum class LedgerBook { WALLET, USER_BANK, PLUGIN, GLOBAL }

data class LedgerEntry(val ownerId: String, val description: String?, val amount: BigDecimal)

data class LedgerOp(val success: Boolean, val balance: BigDecimal?, val message: String? = null)

interface EconomyLedger {
    val backendId: String                 // "base" / "mirai-economy"
    fun start()                           // 后端自检、货币注册、缓存任务
    fun stop()
    fun balance(owner: LedgerOwner): BigDecimal
    fun add(owner: LedgerOwner, amount: BigDecimal): LedgerOp
    fun subtract(owner: LedgerOwner, amount: BigDecimal): LedgerOp
    fun transfer(from: LedgerOwner, to: LedgerOwner, amount: BigDecimal): LedgerOp
    fun total(book: LedgerBook): BigDecimal                  // 银行总额（替代遍历求和）
    fun entries(book: LedgerBook): List<LedgerEntry>          // 迁移 / 排行用
}
```

## 5. 两套实现的映射

### 5.1 BaseLedger（`economy-base`）

| LedgerOwner | account | Scope |
| --- | --- | --- |
| `Wallet(qq)` | `u<qq>` | `DEFAULT` |
| `UserBank(qq)` | `u<qq>` | `BANK` |
| `PluginAccount(id, desc)` | `id` | `PLUGIN` |
| `GlobalAccount(id, desc)` | `id` | `GLOBAL` |

- `BANK` / `PLUGIN` / `GLOBAL` 三个 Scope 由 `BaseLedger.start()` 幂等创建；`DEFAULT` 由 `EconomyCore.init()` 保证。
- **不要把 description 编进 account**：上游 `EconomyAccountRecord` 的主键就是 uuid，`description` 只是可变标签（私银用 `-P/-F/-L` 后缀区分资金池，已经体现在 id 里）。把 desc 编进账户名会让同一个上游账户在 base 侧分裂成多个。当前 `description` 仅作展示提示，不落库。
- `Wallet` / `UserBank` 的 `displayName` 也只服务 mirai 后端：上游 `account(uuid, description)` 会用传入值覆盖 `description` 列，传 null 会把昵称抹成空串，所以门面在有 `User` 时会把 `user.nick` 带下去。
- `add/subtract` 直接 `EconomyAction`；`transfer` 用 `EconomyAction.transfer`（内部已按 id 升序加悲观锁）。
- `total/entries` 走 `economy_account` 按 scope 的 SQL 聚合/查询，**不遍历内存**。

### 5.2 MiraiEconomyLedger（`economy-core`）

上游账户坐标是 `(uuid, context)`，`context` 只有固定几个值（`global-economy` 与各插件的
`plugin.id`），承载不了 base 可自由新增的 scope。因此**只用 `custom(plugin)` 一个上下文**，
把 scope 编码进账户 id 后缀：

| LedgerOwner | 上游账户 id | 上下文 |
| --- | --- | --- |
| `Wallet(accountId)` | `accountId`（无后缀） | `custom(plugin)` |
| `UserBank(accountId)` | `accountId#BANK` | `custom(plugin)` |
| `PluginAccount(id)` | `id#PLUGIN` | `custom(plugin)` |
| `GlobalAccount(id)` | `id#GLOBAL` | `custom(plugin)` |

约定与理由：

1. **`Wallet` 不带后缀**。上游存量钱包本来就落在 `(custom, u<qq>)`，保持同名可以让存量钱包零搬迁直接可用。
2. **分隔符用 `#`**。QQ 号与既有插件账户名都不含该字符。
3. **解码取最后一个 `#` 并校验后缀白名单**。账户名自身含 `#` 不会被截错；未知后缀（如别人手写的 `foo#bar`）整体视为普通账户名，分类为"不属于任何 book"。
4. **`entries` 只按后缀分类**，不再用 `^u\d+$` 区分用户/自定义账户；`WALLET` 额外要求 id 匹配 `^u\d+$`，避免历史裸自定义账户被算进钱包。
5. **附带收益**：`PluginAccount("u999")` 编码成 `u999#PLUGIN`，不再匹配 `^u\d+$`，堵住了"插件账户名误用用户形态"的命名空间风险。
6. 编解码集中在 `MiraiAccountId`，不依赖上游类型，可单测（`MiraiAccountIdTest`，13 例）。

实现要点：

1. 把现有 `EconomyUtil` 的方法体整体搬进 `internal object LegacyEconomyApi`（不上移到 `economy-base`），`MiraiEconomyLedger` 只做 `LedgerOwner → (id, 上下文)` 的翻译并调用它。`EconomyUtil` 则变薄门面。
2. 用户账户统一用 `account(uuid, description)` 定位：上游 `account(user)` 内部就是 `EconomyAccountRecord.fromUser(user)` → `uuid = user.permitteeId.asString()`，与 `account("u<qq>", null)` 命中同一条记录，因此 `MiraiEconomyLedger` 不需要 `User` 对象。
3. `entries` 用 `economyCurrency.balance()` 得到的 `Map<Account, Double>`，key 是 `account.uuid`，再解码后缀分类；上游 `balance()` 对解析不到 User 的 uuid 会退化成 `JpaCustomEconomyAccount`（不抛异常），全量枚举安全。
4. `LegacyEconomyApi.init()` 只做货币注册。2.0.1 之前它还会刷新 `global` 上下文的银行总额缓存并挂 3 小时定时任务，新布局下主银行已不在 global，缓存与任务失去意义且启动即全量扫描，已移除。
5. `start()` 会做一次历史布局残留检测：若旧布局仍有非零余额，说明还没 `migrate`，直接 `Log.warning` 提示（否则用户会看到余额"消失"）。

### 5.3 B 类方法的替代签名

```kotlin
// 旧：以上游类型为参数
fun plusMoneyToBankForAccount(account: EconomyAccount, quantity: Double): Boolean
// 新：以账户 uuid 为参数（uuid = UserInfoDto.id）
fun plusMoneyToBank(ownerId: String, quantity: Double): Boolean
```

`PrivateBankService.payFromOwnerMainBank` 里 `EconomyService.account(accountId, null)` 那一行直接删掉，改传 `accountId`；`getAccountByBank()` 改为 `EconomyUtil.bankEntries(): List<LedgerEntry>`，`BankUsecase` / `BankTaskManager` 各自改为 `LedgerEntry → UserCoreManager.getUserInfo(entry.ownerId)`，并删除 `getUserInfo(account: EconomyAccount)` 重载。

## 6. 配置与启动

`EconomyConfig` 增字段（默认值即用户要求：不配置就是 base）：

```kotlin
@ValueDescription("""
经济后端
BASE：使用本插件自建账户（默认）
MIRAI_ECONOMY：使用上游 mirai-economy 插件（需先安装该插件）
切换后端不会搬迁余额，请先执行 hye economy migrate
""")
var economyBackend: EconomyBackend by value(EconomyBackend.BASE)

@ValueDescription("选择 MIRAI_ECONOMY 但探测不到上游插件时，是否降级为 BASE（true 降级并告警，false 拒绝启动）")
var economyBackendFallback: Boolean by value(true)
```

启动顺序（`HuYanEconomy.onEnable`）：

```
HibernateUtil.init(this)
EconomyCore.init()                      // 无论如何都准备好 base 表，迁移要用
EconomyLedgerProvider.init()            // 探测 → 选择 → start() → 打印实际后端
```

探测与隔离：

```kotlin
internal object MiraiEconomyProbe {
    // initialize = false：只判断类是否存在，不触发上游静态初始化
    fun available(): Boolean = runCatching {
        Class.forName("xyz.cssxsh.mirai.economy.EconomyService", false, javaClass.classLoader)
    }.isSuccess
}
```

`MiraiEconomyLedger` 的硬约束（否则隔离失效）：

- 类字段、父类、构造参数、方法签名**不得**出现上游类型；上游类型只能出现在方法体的局部变量里。
- 实例化整体包 `runCatching`，且捕获 `Throwable`（`NoClassDefFoundError` 不是 `Exception`）。
- `start()` 做一次真实读（`custom(plugin)` 读金币余额），失败即判定后端不可用。

降级日志必须显式，不能静默：

```
[Economy] 配置要求 MIRAI_ECONOMY，但未探测到上游插件 mirai-economy-core，已降级为 BASE
[Economy] 经济后端：BASE（账户表 economy_account / economy_scope）
```

## 7. 切换与资金迁移

### 7.1 为什么必须迁移

两套账本完全独立：切到 BASE 后，旧钱包/银行余额在新表里是 0，用户资产等于清零。**切换动作 = 一次资金搬迁**，不能只改配置。

### 7.2 管理指令（Console，参照 `hye repair`）

```
hye economy status                  # 当前后端、两套账本总额、账户数
hye economy migrate --dry-run       # 只出报告，不写库
hye economy migrate --confirm       # 真正搬迁 mirai → base
hye economy export-base --confirm   # 反向：base → mirai（回滚用）
```

迁移规则：

| 步骤 | 内容 |
| --- | --- |
| 前置 | 建议停服；若在线执行，先全局维护模式，禁止交易 |
| 读取 | `entries(WALLET)` + `entries(USER_BANK)` + `entries(PLUGIN)` + `entries(GLOBAL)`，共 4 组 |
| 映射 | `ownerId` 解析为 qq（`uuid → UserInfoDto.id → qq`）→ `Wallet/UserBank`；解析不出 → `Plugin/Global` |
| 写入 | 目标账户当前余额为 0 才写（幂等）；非 0 视为冲突，跳过并记入报告 |
| 报告 | 源条数/源总额、写入条数/写入总额、跳过明细、两位小数舍入差合计 |
| 回滚 | `export-base` 反向写回上游；上游 `plusAssign` 语义是累加，需先人工核对目标为 0 |

### 7.3 自动迁移（可选开关）

`economyBackendAutoMigrate`（默认 `false`）：仅在 `backend == BASE` 且 base 账户表为空、且上游可用时，启动期自动执行一次 dry-run + 实跑，日志留痕。默认关闭，避免无提示动钱。

## 9. 风险

| 风险 | 说明 | 处置 |
| --- | --- | --- |
| `NoClassDefFoundError` | `EconomyUtil.init` 现在会把它抛出去，直接炸启动 | 所有上游触点包 `runCatching`，捕获 `Throwable` |
| 类加载污染 | 只要 `EconomyUtil` / `BaseLedger` / `Provider` 的常量池里出现上游类型，未装插件的环境仍会在首次加载时失败 | 上游类型限制在方法体；`LedgerIsolationTest` 直接扫 class 常量池把关 |
| 资产清零 | 切 BASE 但没迁移 | `hye economy migrate` 分预演/确认两步；`economyBackendFallback` 只管探测失败，不管迁移 |
| 双账本漂移 | 切走后旧账本仍可被写（上游插件别的功能在写） | 明确旧账本只读；迁移后 `hye economy status` 定期对账 |
| 精度差 | 旧 `Double` → `DECIMAL(19,2)` HALF_UP | 报告里单列舍入差合计，> 阈值时要求人工确认 |
| `take` 有写副作用 | 读余额会创建账户；迁移预演也会顺带建零余额账户 | `total` 走 `entries`（SQL）不调 `take`；迁移只对非零条目写 |
| 并发写 | 迁移期间用户交易 | 停服或维护模式 |

## 10. 验收

1. 未装上游插件 + 默认配置：启动无异常，`status` 显示 `BASE`，jar 的依赖树不含 `mirai-economy-core`。
2. 未装上游插件 + 配置 `MIRAI_ECONOMY` + `fallback=true`：启动成功，日志明确降级。
3. 未装上游插件 + 配置 `MIRAI_ECONOMY` + `fallback=false`：启动失败并给出可读原因（不是堆栈）。
4. 装了上游插件 + `MIRAI_ECONOMY`：余额、银行利息、私银准备金与升级前完全一致。
5. `migrate --dry-run` 报告与库中实际余额逐条对齐；`--confirm` 后 `status` 两账本总额差 < 舍入阈值。
6. `economy-base` 模块边界测试仍通过（不出现 `xyz.cssxsh.mirai.economy`）。

### 11.2 修改

- `utils/EconomyUtil.kt`：改为纯门面，全部委托 `EconomyLedgerProvider.current`，签名保持 `Double`（B 类改为 `accountId: String`；`getAccountByBank()` → `bankEntries(): List<LedgerEntry>`）。
- `constant/Constant.kt`：移除 `CURRENCY_GOLD`（挪到 `LegacyEconomyApi`）。这一步是必须的：`Constant` 是 `object`，`CURRENCY_GOLD` 的类型是上游 `EconomyCurrency`，只要有人引用 `Constant` 就会在未装上游的环境里抛 `NoClassDefFoundError`。
- `config/EconomyConfig.kt`：新增 `economyBackend`、`economyBackendFallback`。
- `HuYanEconomy.onEnable`：`EconomyUtil.init()` → `EconomyLedgerProvider.init()`；`onDisable` 增加 `shutdown()`。
- `command/EconomyCommand.kt`：新增 `hye economy status / migrate / migrate confirm / export-base / export-base confirm`。
- `service/FishingAccountService.kt`：从直连 `EconomyAccount.take` 改为走当前后端——否则后端切到 mirai-economy 后，钓鱼资金会写进另一套账本。
- `service/EconomyAccountAdapters.kt`：删除（`UserInfoDto.economyAccount()` 无条件绑定 base 账户，无调用点）。
- `manager/UserCoreManager.kt`：`getUserInfo(account: EconomyAccount)` → `getUserInfoByAccountId(accountId: String): UserInfoDto?`。
- B 类调用点：`FundingUsecase`、`BankUsecase`、`BankTaskManager`、`RedPackManager`、`PrivateBankService`、`PrivateBankBankruptcyService` 改为传 `accountId`。
- `economy-main/build.gradle.kts`、`economy-game/build.gradle.kts`：删除 `mirai-economy-core` 的 `compileOnly`（这两个模块已无上游引用）；`economy-core` 保留，`LegacyEconomyApi` 编译需要。

### 11.3 有意保留的行为差异

| 位置 | 旧行为 | 新行为 | 原因 |
| --- | --- | --- | --- |

## 12. 布局改造：单上下文 + scope 后缀（2026-10-21）

### 12.1 决策

放弃 `global()` 上下文，mirai 后端**只用 `custom(plugin)`**，base 的 scope 改为编码进账户 id 后缀。

动机：上游 context 是固定值集合（`global-economy` + 各插件 `plugin.id`），本质只有两个可用槽位，
第 5 个 scope 就无处安放。改成 id 编码后，scope 数量不再受上游结构限制，`(account, scope)` 的表达力
在 mirai 侧基本对齐 base。

### 12.2 布局对照

| 位置 | 历史布局（≤ 2.0.1） | 当前布局 |
| --- | --- | --- |
| `Wallet("u1")` | `(custom, u1)` | `(custom, u1)` — 不变 |
| `UserBank("u1")` | `(global, u1)` | `(custom, u1#BANK)` — 换上下文 + 改名 |
| `PluginAccount("p1")` | `(custom, p1)` | `(custom, p1#PLUGIN)` — 改名 |
| `GlobalAccount("g1")` | `(global, g1)` | `(custom, g1#GLOBAL)` — 换上下文 + 改名 |

只有钱包的位置完全不变，其余三项都要搬。**这是本次改造最大的操作风险。**

### 12.3 迁移路径

`migrate` / `exportBase` 不再对称：

| 命令 | 源 | 目标 |
| --- | --- | --- |
| `hye economy migrate` | `MiraiEconomyLedger(LEGACY_CONTEXT)` | `BaseLedger` |
| `hye economy export-base` | `BaseLedger` | `MiraiEconomyLedger(SCOPE_SUFFIX)` |

即：**旧布局的余额只能经 base 中转一次**，不能直接从旧布局改写为新布局（`transferAll` 以 `LedgerBook`
为单位对拷，源和目标若同为上游会互相踩同一批账户）。

`Layout` 枚举就是为了这件事存在的——`LEGACY_CONTEXT` 只允许迁移读取，运行时读写一律 `SCOPE_SUFFIX`。

### 12.4 启动自检

`MiraiEconomyLedger.start()` 在 `SCOPE_SUFFIX` 布局下会扫一遍历史布局，若非零余额 > 0 则
`Log.warning`：

```
mirai-economy 检测到 N 条历史布局余额（钱包在 custom、主银行在 global）。
当前已改用「单上下文 + scope 后缀」布局，这些余额不会被自动读取，
请先执行 hye economy migrate 再切换后端。
```

否则用户切后端后只会看到主银行余额变成 0，没有任何提示。

### 12.6 风险与代价

| 项 | 说明 |
| --- | --- |
| 旧数据搬错 | 只有钱包位置不变，主银行必须走 `migrate`；漏做会让用户看到余额归零（已有启动告警兜底） |
| 跨插件失去共享 | `custom(plugin)` 的 context id 是 `plugin.id`，**别的插件看不到这些余额**。改用 `global()` 时主银行本可与外部插件共享，现在这个能力没有了 |
| 上游生态兼容 | 其它基于 mirai-economy 的插件若按 `^u\d+$` 找用户账户，只能看到钱包（裸 `u<qq>`），看不到 `#BANK` 等账户。这符合预期，但需要在文档里写清楚 |
| 无原子转账 | 上游不暴露事务 API，`transfer` 仍是"先扣后加 + 补偿"；两端虽同上下文也无法真正原子 |
| 账户记录膨胀 | 每个用户在 account_record 里最多 2 条（`u1` 与 `u1#BANK`），`description` 会被各自覆盖，不影响唯一性 |

## 13. 首个业务接入：签到（2026-10-21）

### 13.1 为什么从签到开始

签到是资金链最简单、使用频率最高的功能：只有"给钱包加一笔固定奖励"和"读一次余额回显"
两个动作，没有转账、没有负数、没有多账户协作。用它验证"业务代码可以不感知后端"这个前提，
代价最小、暴露问题最快。

### 13.2 新增 `ledger/UserWallet.kt`

业务级钱包门面（`BigDecimal` 语义），构造时可注入 [EconomyLedger]：

```kotlin
class UserWallet(private val ledger: EconomyLedger = EconomyLedgerProvider.current)
```

| 成员 | 作用 |
| --- | --- |
| `balance(qq)` | 读钱包余额 |
| `credit(qq, amount, nickname)` | 入账，返回 `LedgerOp`（成功时带**入账后**余额） |
| `debit(qq, amount, nickname)` | 扣款，余额不足返回失败 |
| `UserWallet.money(Double)` | 两位 HALF_UP 舍入，统一精度入口 |
| `UserWallet.accountId(qq)` | `qq → "u<qq>"`，与 `UserInfoDto.id` 同构 |

这一层存在的理由是把三件事收敛到一处：账户标识拼接、金额精度、失败语义。业务层不再
手写 `"u$qq"`、不再 `BigDecimal.valueOf(...)`、不再把 `Boolean` 当结果。

### 13.3 签到改动

| 位置 | 改动 |
| --- | --- |
| `SignUsecase.sign` 步骤 5 | `EconomyUtil.plusMoneyToUser(user, gold)` → `UserWallet().credit(userInfo.qq, money(gold), userInfo.name)` |
| `SignUsecase.sign` 步骤 7 | `EconomyUtil.getMoneyByUser(user)` → 复用入账返回的 `credit.balance`，为空才回查 |
| `SignOutcome.gold` | `Double` → `BigDecimal`（代表真实入账金额） |
| `SignRules.logCommitted` | 日志用 `toPlainString()`，保持两位小数 |
| `SignUsecase` import | 移除 `model.user.user`（不再需要 mirai `User` 对象） |

**为什么用 `userInfo.qq` 而不是 `userInfo.user`**：`User` 是 mirai 运行期对象，
而账本只需要 `u<qq>` 这个字符串。去掉这层依赖后，签到入账逻辑可以在没有 mirai 运行时的
测试环境里跑到真实数据库上（见 13.4）。
